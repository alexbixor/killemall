128x96 LoRes, 256 colours, >= 25 fps, running the SAME game logic and the SAME levels as the 48K/128K editions.

Everything in v0.1 that is not changed below applies unchanged: section 0 (vocabulary, smul_shr, ROW), section 1
(screen, palette), section 2 (camera, rays, SIN/COS/RECIP tables), section 3 (projection), section 5 (plane pixel

## 1. Level = the tape editions' level (tools/mapc.py output, edition "next")
- Bytes: 'K', 1, w=32, h=32, sx, sy, start_angle (256 units per turn: E 0, S 64, W 128, N 192), n_things; then 1024 cell
  bytes row-major (offset = my*32 + mx); then n_things x (type, x, y). Loaded at LEVEL (0B800h) exactly as emitted.
- Cell codes: 0 floor (walkable); 1..7 wall; 8 door; 9 red door; 10 blue door; 11 secret wall; 12 exit. Every code != 0
  is solid for the renderer. Outside the map = solid stone. The game logic opens a door by writing 0 into the cell (as
  the tape editions do); the renderer only ever reads the cell bytes.
- Wall texture per code (walls.bin ids, section 6 of v0.1): WALLMAP = [-, 0 stone, 1 brick, 3 iron, 8 blue stone,
  2 moss, 13 crumbling, 14 vines, 4 wood door, 5 RED DOOR, 6 BLUE DOOR, 0 stone (secret: looks like code 1), 7 EXIT].
  Texture ids 5, 6, 7 (option A's dais, lintel, altar) are REGENERATED by tools/nx_textures.py as: 5 = iron-banded door
  with a red lock plate, 6 = the same with a blue plate, 7 = exit portal (stone frame, glowing centre). Ids 0-4 and 8-15
  must stay byte-identical (prove with md5 of each 4 KB texture block before/after). manifest.json names updated.
- Camera from the header: px = sx*256 + 128, py = sy*256 + 128 (Q8 cell centre), a = start_angle * 4 (0..1023).
- The player start cell and the things are NOT cells: mapc.py leaves code 0 where '@' and the thing letters stood
  (they are walkable floor; the renderer never sees things).
- The mapc .bin may hold several levels back to back (one 8-byte header + 1024 cells + things each); the Next build tool
  copies ONE level (the first, or --level-index n) to LEVEL. Level 01 compiles to 1063 bytes; LEVEL has 2048.
- Optional header lines for the Next only (other editions ignore them): `#ceil=32` or `#ceil=64` (ceiling height
  H32, default 32), `#ftex=<floor name>` (default flag), `#ctex=<ceiling name>` (default plaster), names from
  manifest.json "floors". mapc.py does not need to parse them: the Next build tool reads the .txt header directly and
  stores CEIL, FTEX, CTEX in main_vars (bytes) at build time.

## 2. Heights (the whole point of edition B)
- Every walkable cell: floor = 0, ceiling = CEIL (32 or 64, per level), eye = 22 (H32), HOR = 48.
- With v0.1 section 3: y_floor(d) = 48*256 + 22*R(d) ; y_ceil(d) = 48*256 - (CEIL - 22)*R(d) ; both clamped to int16.

## 3. The column walk (per column c = 0..127)
1. Ray and DDA exactly as v0.1 section 2 and section 4 steps 1 and 4 (d, side, mx/my advance, sat_add, d = max(d, 8)),
   but the loop runs until cell(mx, my) is solid (code != 0 or outside the map), at most 64 steps. If d > 4095 or the ray
   leaves the map or 64 steps pass: VOID(c, 0, 96), ZBUF[c] = 4095, next column (cannot happen on a mapc level: the
   outer wall is closed - still implement it).
2. Hit column u and shade s exactly as v0.1 section 4 item 4 (hit = py + smul_shr(ry, d, 8) if side == 0 else
   px + smul_shr(rx, d, 8); u = (hit & 255) >> 3; s by 384/768/1536, +1 (max 3) when side == 1).
3. tex = WALLMAP[code]. WALL(c, CEIL, 0, tex, d, u, s) with ytop = 0, ybot = 96, exactly the v0.1 WALL tile split
   (CEIL = 64 gives two tiles: heights 64..32 and 32..0; CEIL = 32 gives one). Pieces are emitted top-down.
4. Floor: a = ROW(y_floor(d)); if a < 96: PLANE_ADD(c, 0, FTEX, a, 96).
   Ceiling: b = ROW(y_ceil(d)); if b > 0: PLANE_ADD(c, CEIL, CTEX, 0, b).
5. ZBUF[c] = d.
Record order per column (for the records oracle): floor plane, ceiling plane, wall pieces top-down.
Equivalence: on a level converted to v0.1's 4-byte cells (floor 0, ceil CEIL, solid|wtex, ftex|ctex<<4) the v0.1
walker + coalescer produces the same PIXELS (its per-step floor/ceiling spans chain into exactly these two spans); the
v0.1 reference renderer run on the converted level is therefore an independent pixel oracle for edition B.

## 4. Pixels
- DRAW_PIECE, PLANE_ADD, VOID pixel rules: v0.1 sections 4 and 5 unchanged. src/next/draw.asm is the starting point;
  copy it to src/next/draw_b.asm and optimise freely (the pixel oracle decides, not the source). tools/m30_bench_gen.py
  contains the fastest known drawers for this screen (wall column: 48 unrolled row pairs, exit through a patched RET;
  plane row: texel index = (L and F0h) or (D and 0Fh), two pixels per PUSH with SP at the row end) - lift them.
- Plane tiers. The gate (section 6) decides which tier ships; the reference (section 5) implements all three behind a
  flag so the oracle is green for whichever one ships:
  - "planes-hi": v0.1 section 5 exactly (every pixel its own texel).
  - "planes-lo": pixel (c, y) of a plane row uses wx, wy computed for column (c & 0xFE): pixels 2k and 2k+1 share a texel.
  - "planes-flat": no texture; a plane row y is filled with palette index material*16 + level where material = the
    tier's colour (floor: manifest "flag" material 6, ceiling: "plaster" 7) and level = 12 - 3*s (s = shade of the row's
    depth d by the wall thresholds), rows with d > 4095 = index 0. Same row maths as section 5 up to the shade.
  Ship the richest tier that keeps the gate. Report the measured fps of every tier in build/night/N1_result.out.

- src/next/main_b.asm: lane M's loop (keys, 50 Hz time base, setup_camera, collision against the mapc cells: a cell is
  walkable iff its code is 0; WALL_MARGIN as main.asm), the new walker, draw.asm, frames/px/py/ang/ticks at 5800h..5809h

  working for main.asm).
- Gate: >= 25 fps on the "engine speed" line of tools/nx_walk_video.py along a scripted path in level 01 (start, down
  the corridor, through the door area, turn, back), 28 MHz, textured planes (hi or lo). Budget evidence per component
  (walk, wall pieces, planes) in build/night/N1_result.out, measured by stubbing as lane S did.
- Tier order: planes-hi, then planes-lo, then planes-flat (section 4). The first tier that measures >= 25 fps along the
  whole scripted path ships. If even planes-flat misses 25 fps, ship planes-flat anyway and report the number - a
  slower frame is not a reason to stop; a wrong pixel is.
